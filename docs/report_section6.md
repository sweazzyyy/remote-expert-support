## 6.1 Модель бизнес-процесса в нотации BPMN 2.0

Текстовое описание процесса «Проведение дистанционного экспертного сеанса поддержки при ремонте оборудования» (раздел 3) переведено в нотацию BPMN 2.0 [16]. Диаграмма построена в draw.io элементами библиотеки BPMN 2.0 (рисунок 6.1).

Процесс изображён одним пулом «Система удалённой экспертной поддержки», в котором три дорожки (lanes): «Полевой инженер», «Диспетчер / модуль маршрутизации», «Удалённый эксперт». Пользовательские задачи отмечены маркером «человек», автоматические (сервисные) задачи отмечены маркером «шестерёнка» и выделены цветом.

Ход процесса:
1. Стартовое событие «Обнаружена неисправность». Инженер выполняет задачу «1. Сформировать карточку инцидента».
2. Исключающий шлюз «Категория определена?». При ответе «Нет» инженер выполняет задачу «Уточнить категорию и описание» и возвращается к карточке. При ответе «Да» заявка переходит к модулю маршрутизации.
3. «2. Приоритизировать очередь инцидентов»: система упорядочивает открытые заявки по весу приоритета (Алгоритм 2).
4. «3. Подобрать эксперта по профилю»: система выбирает эксперта по совпадению навыков и рейтингу (Алгоритм 1).
5. Шлюз «Эксперт найден?». При ответе «Нет» срабатывает промежуточное событие-таймер «Ожидание эксперта», затем очередь приоритизируется заново. При ответе «Да» выполняется следующий шаг.
6. «4. Установить P2P WebRTC-сессию».
7. Эксперт выполняет «5. Нанести AR-метку на видеокадр», инженер выполняет «6. Выполнить ремонт по AR-указателям».
8. Шлюз «Дефект устранён?». При ответе «Нет» эксперт наносит новые метки (возврат к задаче 5). При ответе «Да» эксперт выполняет «7. Оформить протокол заключения».
9. Конечное событие «Инцидент закрыт».

У каждого шлюза есть обе ветви, и каждая задача лежит на пути от стартового события к конечному.

**Таблица 6.1 — Автоматизируемые операции**

| № | Операция (задача на диаграмме) | Что делает система | Функция в коде (src/main.py) |
|---|---|---|---|
| 1 | 1. Сформировать карточку инцидента | Создаёт запись INCIDENT со ссылками на оборудование, инженера и уровень приоритета, вес берёт из справочника PRIORITY, требуемые навыки сохраняет в INCIDENT_SKILL | `create_incident()`, `get_priority_weight()` |
| 2 | 2. Приоритизировать очередь инцидентов | Сортирует очередь открытых инцидентов по убыванию веса приоритета слиянием, O(n log n) (Алгоритм 2) | `prioritize_incidents_queue()`, `merge_incidents()` |
| 3 | 3. Подобрать эксперта по профилю | Для каждого активного эксперта считает число совпавших навыков и выбирает максимум по score = совпадения·100 + рейтинг (Алгоритм 1), затем создаёт запись EXPERT_ASSIGNMENT | `assign_best_expert()`, `create_assignment()` |
| 4 | 4. Установить P2P WebRTC-сессию | Создаёт сессию SESSION для назначения: уникальный room_id, параметры качества связи | `setup_webrtc_session()` |
| 5 | 5. Нанести AR-метку на видеокадр | Сохраняет векторную метку ANNOTATION (инструмент, координаты x1, y1, x2, y2, цвет) и передаёт её инженеру | `process_ar_annotation()` |
| 6 | 7. Оформить протокол заключения | Сохраняет протокол PROTOCOL по сессии и переводит инцидент в статус resolved | `generate_consultation_protocol()` |

## 6.2 Логическая модель данных в 3НФ

Модель построена в нотации Crow's Foot (рисунок 6.2). В ней 11 сущностей: 8 основных, справочник PRIORITY и две ассоциативные сущности для связей «многие-ко-многим».

**Таблица 6.2 — Сущности модели данных**

| Сущность | Назначение | Ключ | Атрибуты |
|---|---|---|---|
| USER | Пользователь системы: инженер, эксперт, диспетчер | PK user_id | full_name, email, role, rating, is_active |
| SKILL | Справочник навыков (компетенций) | PK skill_id | name |
| USER_SKILL | Навыки эксперта (M:N USER–SKILL) | PK (user_id, skill_id), оба FK | — |
| EQUIPMENT | Единица обслуживаемого оборудования | PK equipment_id | serial_num, model, location |
| PRIORITY | Справочник уровней приоритета | PK priority_level | weight |
| INCIDENT | Карточка инцидента (неисправности) | PK incident_id | FK equipment_id, FK engineer_id, FK priority_level, title, description, category, status, created_at |
| INCIDENT_SKILL | Навыки, требуемые для инцидента (M:N INCIDENT–SKILL) | PK (incident_id, skill_id), оба FK | — |
| EXPERT_ASSIGNMENT | Назначение эксперта на инцидент (результат Алгоритма 1) | PK assignment_id | FK incident_id, FK expert_id, score, assigned_at |
| SESSION | WebRTC-сеанс по назначению | PK session_id | FK assignment_id, room_id, quality, established_at |
| ANNOTATION | AR-метка, нанесённая в сеансе | PK annotation_id | FK session_id, tool_type, x1, y1, x2, y2, color, created_at |
| PROTOCOL | Протокол экспертного заключения | PK protocol_id | FK session_id (UNIQUE), expert_notes, closed_at |

**Таблица 6.3 — Связи модели данных**

| Родитель | Потомок | Тип | Внешний ключ | Смысл |
|---|---|---|---|---|
| USER | USER_SKILL | 1 : 0..N | USER_SKILL.user_id | эксперт имеет навыки |
| SKILL | USER_SKILL | 1 : 0..N | USER_SKILL.skill_id | навыком владеют эксперты |
| INCIDENT | INCIDENT_SKILL | 1 : 1..N | INCIDENT_SKILL.incident_id | инцидент требует хотя бы один навык |
| SKILL | INCIDENT_SKILL | 1 : 0..N | INCIDENT_SKILL.skill_id | навык требуется в инцидентах |
| USER | INCIDENT | 1 : 0..N | INCIDENT.engineer_id | инженер создаёт инциденты |
| EQUIPMENT | INCIDENT | 1 : 0..N | INCIDENT.equipment_id | инциденты по оборудованию |
| PRIORITY | INCIDENT | 1 : 0..N | INCIDENT.priority_level | уровень приоритета инцидента |
| INCIDENT | EXPERT_ASSIGNMENT | 1 : 0..N | EXPERT_ASSIGNMENT.incident_id | назначения по инциденту (0, пока эксперт не найден) |
| USER | EXPERT_ASSIGNMENT | 1 : 0..N | EXPERT_ASSIGNMENT.expert_id | эксперт получает назначения |
| EXPERT_ASSIGNMENT | SESSION | 1 : 0..1 | SESSION.assignment_id | по назначению проводится сеанс |
| SESSION | ANNOTATION | 1 : 0..N | ANNOTATION.session_id | AR-метки сеанса |
| SESSION | PROTOCOL | 1 : 0..1 | PROTOCOL.session_id (UNIQUE) | сеанс завершается протоколом |

Через назначение сессия однозначно связана с инцидентом и экспертом, поэтому отдельные incident_id и expert_id в SESSION и PROTOCOL не хранятся: они были бы транзитивно зависимыми копиями.

Обоснование нормализации:
1. **1НФ.** Все атрибуты атомарны. Координаты AR-метки хранятся четырьмя скалярными атрибутами x1, y1, x2, y2 вместо составного coordinates_json. Списки навыков эксперта и инцидента вынесены из строк в ассоциативные сущности USER_SKILL и INCIDENT_SKILL, поэтому повторяющихся групп нет.
2. **2НФ.** У сущностей с составным ключом (USER_SKILL, INCIDENT_SKILL) нет неключевых атрибутов. У остальных сущностей ключ простой, частичных зависимостей нет.
3. **3НФ.** Транзитивные зависимости устранены. Вес приоритета зависит от уровня приоритета, а не от инцидента, поэтому он вынесен в справочник PRIORITY. Модель, серийный номер и расположение оборудования вынесены в EQUIPMENT. Инцидент и эксперт сессии определяются через EXPERT_ASSIGNMENT и в SESSION не дублируются.

**Таблица 6.4 — Соответствие модели и кода (src/main.py)**

| Сущность | Структура в коде |
|---|---|
| USER + USER_SKILL + SKILL | словарь эксперта: user_id, full_name, role, rating, is_active, список skills |
| EQUIPMENT | словари списка equipment |
| PRIORITY | функция get_priority_weight(): critical 100, high 75, medium 50, low 25 |
| INCIDENT + INCIDENT_SKILL | create_incident(): incident_id, equipment_id, engineer_id, priority_level, title, description, category, status, created_at, required_skills |
| EXPERT_ASSIGNMENT | create_assignment(): assignment_id, incident_id, expert_id, score, assigned_at |
| SESSION | setup_webrtc_session(): session_id, assignment_id, room_id, quality, established_at |
| ANNOTATION | process_ar_annotation(): annotation_id, session_id, tool_type, x1, y1, x2, y2, color, created_at |
| PROTOCOL | generate_consultation_protocol(): protocol_id, session_id, expert_notes, closed_at |

Поле weight в словаре инцидента не хранится как самостоятельные данные: это значение, прочитанное из справочника PRIORITY при создании карточки, чтобы сортировке не приходилось обращаться к справочнику.

## 6.3 Алгоритмы автоматизируемых операций

### Алгоритм 1: assign_best_expert (операция 3, рисунок 6.3)

На блок-схеме показаны внешний цикл по экспертам (условие i < n, возврат после i = i + 1), проверка активности эксперта, вложенный цикл по навыкам инцидента (условие j < m, возврат после j = j + 1), проверка вхождения навыка в список навыков эксперта и обновление максимума. У каждого ромба два выхода, «Да» и «Нет».

- **Время в худшем случае: O(n · m · s)**, где n — число экспертов, m — число навыков инцидента, s — наибольшее число навыков у одного эксперта. Внешний цикл выполняется n раз, вложенный m раз. Проверка `skill in expert["skills"]` — линейный поиск по списку, в худшем случае s сравнений.
- **Память: O(1)**, используются только скалярные переменные (best_expert, max_score, matched, score, i, j).
- Если хранить навыки эксперта во множестве (set), проверка вхождения в среднем занимает O(1) и общее время равно O(n · m) при дополнительной памяти O(s) на построение множества. В текущей реализации используется список, поэтому верна оценка O(n · m · s).

### Алгоритм 2: prioritize_incidents_queue + merge_incidents (операция 2, рисунок 6.4)

Блок-схема состоит из двух частей:
а) рекурсивная функция: ветка базового случая (len(queue) ≤ 1, очередь возвращается без изменений), вычисление mid, два рекурсивных вызова (символ «предопределённый процесс») и вызов слияния;
б) функция слияния: цикл сравнения left[i].weight ≥ right[j].weight с возвратом к условию, затем два цикла дописывания остатков левого и правого списков.

- **Время: O(n log n)** в худшем, среднем и лучшем случае. Глубина рекурсии ⌈log₂ n⌉, на каждом уровне слияние суммарно обрабатывает n элементов.
- **Память: O(n)** на временные подсписки и результат слияния, плюс O(log n) на стек рекурсии.
- Сортировка устойчива: при равных весах сохраняется порядок поступления заявок.
